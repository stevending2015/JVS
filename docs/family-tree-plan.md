# 家族树模块 · 设计方案（待确认）

> 状态：调研完成，**尚未开始编码**。确认本方案后再动手。

## 一、调研结论

### 1. 数据模型：GEDCOM 7 是行业标准

[GEDCOM 7](https://gedcom.io/specifications/gedcom7-rc.pdf)（FamilySearch 维护）用**双记录模型**：

```
n @XREF:FAM@ FAM          {1:1}   ← 家庭单元
+1 HUSB @<XREF:INDI>@     {0:1}
+1 WIFE @<XREF:INDI>@     {0:1}
+1 CHIL @<XREF:INDI>@     {0:M}
```

原文几条关键约束：

- **连线必须双向一致**：`FAM.HUSB/WIFE` ⇄ `INDI.FAMS`；`FAM.CHIL` ⇄ `INDI.FAMC`
- **多次婚姻 = 多条 FAM 记录**，一对配偶只应有一条 FAM
- `CHIL` 顺序应**按出生时间**排列
- **`HUSB`/`WIFE` 只是布局提示，不得据此推断性别或角色**（对入赘等情形很重要）
- 该结构将来会扩展以更好表达多样的人类亲属关系

### 2. 中式族谱体例

传统族谱把图形叫**世系图**、把逐人著录叫**世系表/齿录**。常用字段：讳（本名）、字、号、生卒、配氏（配/继配/侧室）、子嗣、排行、葬处、籍贯。修谱体例中还有：

- **世次**（第几世）、**房支**（按子分）、**字辈/派语**（每代用固定字）
- **过继/入嗣/出继/归宗/入赘** 等特殊关系，团体标准明确要求「世系内容在入嗣方法中记述」——即**入嗣方式必须是显式字段**，不能靠备注猜
- 参考标准：T/QZAS 051-2025《族谱数字化规范》（但该标准讲的是**扫描加工流程**，不含数据格式）

### 3. 现有中文产品的交互形态

参考 [MyFamilyTree](https://github.com/Asketisch/FamilyTree)：树形图（无限层级）+ 按世代分组的列表视图 + 轴对称布局 + 滚轮缩放自动居中 + 实时搜索高亮 + 点击查看详情与关系网络 + 数据一致性校验。

## 二、数据模型：两个方案对比

### 方案 A：沿用现有 `relation` 边表

```
relation(from_person_id, to_person_id, kind)   -- parent_father / parent_mother / spouse / sibling
```

- 优点：表已存在，改动最小
- 缺点：
  1. **兄弟是派生关系**却要存，等于存冗余，必然不一致
  2. 无法表达「家庭单元」——布局时仍要从边反推夫妇与子女
  3. 多次婚姻、过继、继子女表达混乱（一条 spouse 边说不出是初婚还是继配）
  4. 一条边的两端都要改，容易写成半对

### 方案 B：GEDCOM 式「个人 + 家庭单元」（**推荐**）

```sql
-- 个人（复用现有 person，仅扩展字段）
person(id, name, gender, ..., generation, generation_char, courtesy_name, art_name,
       ranking, native_place, burial_place, ...)

-- 家庭单元：一对配偶 + 其子女
family(id TEXT PK, husband_id TEXT, wife_id TEXT, kind TEXT,
       marriage_date TEXT, divorce_date TEXT, note TEXT,
       created_at, updated_at, deleted_at)

-- 子女挂到家庭单元上，并记录入嗣方式
family_child(id TEXT PK, family_id TEXT, child_id TEXT,
             pedigree TEXT,      -- birth/adopted/step/foster/过继/入赘
             birth_order INTEGER,
             created_at, updated_at, deleted_at)
```

- 优点：
  1. 与行业标准一致，将来能**导入/导出 GEDCOM 对接国际族谱软件**
  2. 天然表达多次婚姻、过继、继子女
  3. **布局直接以家庭单元为节点**，不需要反推
  4. 一致性可由仓储层单点保证（写 FAM 时同步校验）
- 代价：一次 schema 迁移（`relation` 表目前**没有任何数据**，风险极低）

**结论：采用方案 B。** 迁移方式：`SCHEMA_VERSION` 1 → 2，新建 `family` / `family_child`，删除未使用的 `relation`（DDL 用 `DROP TABLE IF EXISTS`，因为该表从未写入过）。

## 三、中式扩展字段（分两批）

**P1 必做**（影响布局与检索）：
- `person.generation` 世次（数字，1 = 始祖）
- `person.generation_char` 字辈用字
- `person.courtesy_name` 字、`person.art_name` 号
- `family_child.pedigree` 入嗣方式：亲生 / 过继 / 收养 / 继子女 / 入赘

**P3 可选**（著录完整度）：
- `person.ranking` 排行、`native_place` 籍贯、`burial_place` 葬处
- `family.kind`：初婚 / 继配 / 侧室 / 入赘 / 未婚

**明确不采用**传统「女不入谱」：默认男女平等入谱，只提供「仅显示男性后裔」的**可选筛选**。

## 四、三视图与交互

### 视图 1：世系图（树形，主视图）
- 自上而下；同一世代同一水平线，左侧标「第 N 世」
- **夫妇并排组成一个家庭单元节点**；子女从该单元底部挂出
- 多次婚姻向右分叉，各自带自己的子女
- 顶部根节点：默认「本人」，可切换任意人为临时根

### 视图 2：世代列表（齿录，快速浏览与编辑）
- 按世次分组，每行：姓名 + 字号 + 生卒 + 配偶 + 子女数
- 适合 50–300 人规模；也是「世系图太大」时的降级视图

### 视图 3：人物详情（侧栏或弹窗）
- 基本资料、父母、配偶（含婚次）、子女
- 关系网络摘要（父系/母系分支）
- 操作入口：编辑资料、添加父亲/母亲/配偶/子女

### 交互
- 滚轮缩放（0.4×–2×）、拖拽平移、双击居中、「定位到本人」
- 搜索框高亮定位（复用生日模块的搜索思路）
- 添加关系时**复用现有 person 弹窗表单**，只多一个「关系类型」选择

## 五、布局算法与性能

- 家族树本质是**树/森林**，不是任意图 → 用 **Reingold–Tilford / Walker tidy tree**（自研约 150 行，不引第三方依赖）
- 家庭单元作为布局节点，宽度 = 夫妇两人宽度；子女行居中
- 连线用正交折线：父母中点 → 子女顶部
- **规模**：≤300 人纯 SVG 直出；>300 人自动建议切换到「世代列表」或按房支分页
- 不引入 dagre/elkjs：它们解决任意图布局，对家族树是过度设计且体积大
- **环检测**：近亲婚配会产生环，布局前检测；检测到就降级为列表视图并提示，不做花式处理

## 七、风险与取舍

1. **一致性是生命线**：写家庭单元时必须同步校验（如「A 的父 = B 的夫」），否则数据烂掉后无法修复。仓储层强制，不依赖 UI。
2. **环**：不做通用图布局，遇到环降级提示。
3. **隐私**：家族树含在世亲属生辰。目前数据全在本机 SQLite，但**导出/分享必须显式确认**。
4. **不引第三方族谱库**：体积与维护成本不划算，自研布局约 150 行可控。

## 九、实施结果（已完成）

按本文方案实施，四个决定全部落地：

| 决定 | 实施 |
| --- | --- |
| GEDCOM 式家庭单元模型 | ✅ `family` + `family_child`，`relation` 边表已删除（曾为空表） |
| 完整中式著录 | ✅ 世次、字辈、字、号、排行、籍贯、葬处、卒；`family.kind`（初婚/继配/侧室/入赘/未婚）；`pedigree`（亲生/收养/继子女/寄养/过继/入赘） |
| 本人为根 | ✅ 默认根：本人 → 无父母者（始祖）→ 第一人；可随时切换根节点 |
| GEDCOM 导出 | ✅ `docs` 中所述 P4 已实现，导出 GEDCOM 7.0（HEAD/INDI/FAM/TRLR） |

### 额外发现并修掉的两个问题

1. **出生日期必须可缺失**。先人常无生卒记载，原仓储层强制校验日期，导致添加祖先失败。
   现在「全部日期字段为空」视为**未知**（允许），但「部分填写」仍是错误——那是笔误，不是缺信息。
2. **世次必须由关系推导**。配氏在传统族谱中随夫世次。现在仓储层在 `addParent` /
   `addSpouse` / `addChild` 时若表单未填世次，按关系自动继承（父→子 +1，配偶同世次）。
   放在仓储层而不是 UI，保证任何调用方都不会写出不一致的数据。
